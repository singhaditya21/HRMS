## Part A — Standing rules (apply everywhere, no exceptions)

1. **Markers.** Use the PRD's existing markers: **[Verified]**, **[Hypothesis]**, **[Killed]**. Add **[Reversed]** for a conclusion this PRD previously stated and now retracts. Mirror-sourced findings are **[Verified — mirror]** and must say "pull from the primary source before customer use".
2. **Never invent** a number, rate, threshold, section number, rule number, form number, date, price, file field, API name or competitor feature. If it is not in this ledger or the research files, write that it is unknown and route it to §20's validation plan. Fabricated precision is the failure mode four research rounds were built to hunt.
3. **Cite evidence IDs.** When you state a fact from Part C, cite its `EV-###` ID. Do not mint EV IDs yourself — only §02 (evidence-ledger) adds rows, and it adds exactly the IDs in Part C.
4. **Legal statements** follow Part D. When unsure whether something is safe to state, it is not — say "counsel required" and route to §23.
5. **Mermaid safety.** In `stateDiagram-v2` and `sequenceDiagram` labels: no `;` (it silently splits the label into a stray statement and the parser does NOT catch it), and avoid `->`, `<=`, `>=`, `<`, `>` and parentheses. Write words instead ("at least", "up to", "leads to"). Validate every diagram you create or edit. New diagram keys must start with your section key (e.g. `fr-payroll-ecr-return-types`). **Do not edit shared diagrams** (list in Part F) — create a new key instead.
6. **ID conventions.** Keep your section's existing requirement format (block-style or table-style). New requirement IDs continue from your section's current maximum. New sections use the prefixes assigned in Part F.
7. **Cross-references** use this PRD's own numbering, zero-padded: `§08`, `§08.3`. Sections 01–20 keep their numbers; **§21, §22 and §23 are new** (Part F). Never reference an earlier draft's numbering. If you find an unpadded or ambiguous reference in your section, fix it to point at the correct section of *this* PRD.
8. **Edit only your own section file(s)** and diagrams whose keys start with your section key. Never touch another section's file.
9. **Voice.** Keep the PRD's existing tone — direct, evidence-led, no marketing. Any competitor claim needs a capture date and a note of whether the product was executed or only its documentation read. Never assert that a competitor's published data "is wrong" as a sales claim.
10. **Length target** (Part F) is to be reached with **specification depth** — requirements, acceptance criteria, data definitions, worked examples, edge cases, decision tables, test scenarios, diagrams. **Never pad, repeat, or restate other sections.** A reviewer will check.

### C.2 Statutory — EPF/ECR  _(research: r5/02-ecr-spec-and-tds-file-formats.md)_

- **EV-035** [Verified] ECR text file: delimiter `#~#` (**three** characters), **no header row**, **11 fields in order**: UAN, Member Name as per UAN, Gross Wages, EPF Wages, EPS Wages, EDLI Wages, Employee PF Contribution, Employer EPS Contribution, Employer PF Contribution, NCP Days, Refund of Advance. Wage Month, Return Type, Contribution Rate and Remark are portal form controls, not file content. No filename pattern is mandated. **The re-engineered ECR (beta, from wage month September 2025) did not change the layout.** The generator is buildable.
- **EV-036** [Verified] Return submission is separated from payment: upload → validate → return statement → approve/reject → Due Deposit Balance Summary → challan with TRRN → pay → receipt. **An approved return can never be cancelled.** Multiple challans are permitted.
- **EV-037** [Verified] Three return types: **Regular**; **Supplementary** (needs an approved Regular, may be filed repeatedly, may contain only members absent from all prior returns for that month); **Revised** (needs an approved Regular, no other return in process, **no payment initiated**, overwrites prior data). ⇒ Downward correction is only possible before payment initiation — **the verification gate belongs immediately before payment initiation.**
- **EV-038** [Verified] Strict month-wise chronological filing, with a four-month transitional relaxation: a Regular return for month M is allowed only if returns for all active members of month M−4 have been filed. A skipped month blocks later months.
- **EV-039** [Verified] Interest under s.7Q is **mandatory and auto-calculated**; damages under s.14B may be deposited later at the employer's option. A cash-flow requirement.
- **EV-040** [Verified] Only the age-58 EPS rule is a hard system block. "Joined after 1 Sep 2014 with wages above ₹15,000" is a **flag** shown before filing, not a rejection. Contributions permitted only between valid date of joining and date of leaving; rate must be statutory or higher.
- **EV-041** [Verified] Correcting a wrongly recorded date of exit requires a **joint declaration** by employer and employee — an offline dependency that can block a month's filing.
- **EV-042** [Verified] NIL months use no file; admin/inspection charges are paid via Direct Challan Entry, enabled only when there are no active members.
- **EV-043** [Verified] Arrears use a separate "File Arrear Return" flow; **no arrear file layout is published**. Do not specify an arrear file format — fence it.
- **EV-044** [Verified] Part-payment contribution file: 6 fields, `#~#`-separated — UAN, MEMBER_NAME, EPF_CONTRIBUTION, EPS_CONTRIBUTION, EPF_EPS_DIFF_CONTRIBUTION, REFUND_OF_ADVANCES.

- **EV-064** [Verified — not in force] DPDP r.6(1)(a) names encryption, obfuscation, masking and virtual tokens; r.6(1)(c) requires logging able to **detect** unauthorised access, not merely record it.
- **EV-065** [Verified] Significant Data Fiduciary status arises only by notification under s.10(1); no threshold triggers it; s.10 is not in force; we are not aware of any designation as of September 2026.
- **EV-066** [Verified] DPDP Chapter III contains exactly four rights: access (s.11), correction and erasure (s.12), grievance (s.13), nomination (s.14). **No right against automated decisions, no right to explanation, no right to human review.** ss.11–12 are textually tied to consent (including s.7(a)); whether they reach s.7(i) employment processing is a counsel question.

- **EV-068** [Verified] Aadhaar (Sharing of Information) Regulations 2016: reg 5 is the basis for a non-requesting employer to collect and store an Aadhaar number (lawful purpose + three-part disclosure + consent); reg 6: security and confidentiality (6(2)), redaction before any database is made public (6(3)), **encrypted transmission (6(4)) — a legal requirement**, retention ceiling tied to the consented purpose (6(5)); reg 7 deems contravention a s.29(2) violation.
- **EV-069** [Verified] Aadhaar s.8A(4)(b): a registered Offline Verification Seeking Entity may not collect, use or store an Aadhaar number — no consent exception. **Storing Aadhaar numbers and holding OVSE registration cannot coexist in one legal entity** (corporate-structure decision; route to counsel before acting).
- **EV-070** [Verified] AOVR 2021 reg 16A(2): no offline verification on behalf of another entity; reg 15(2): no e-KYC licence-key sharing ⇒ **a multi-tenant "we verify Aadhaar for your employees" feature cannot be built.** Reg 4A(4): Virtual ID may not be stored by any entity.

Never write "a face template is not biometric information under the Aadhaar Act".

## Part E — Architecture corrections

Apply in the sections named in Part F.

1. **State machines.** Payroll month: `OPEN → INPUTS_CLOSED → PROCESSED → APPROVED → LOCKED → DISBURSED → PAYMENT_INITIATED → FILED`, reversible before LOCK. The statutory **verification gate sits immediately before PAYMENT_INITIATED** (EV-037). Filing machine gains **REJECTED**, **REVISED** and **SUPPLEMENTARY** states. A post-FILED correction path exists and is a **diff, never a mutation**. Present each machine as a **transition table** (event · guard · side effect · who may trigger), with the diagram as illustration.
2. **Bitemporality scoped by entity class.** Bitemporal (never-forget, replayable): rules, salary structures, assignments, statutory attributes. **Not** bitemporal (erasable): punches, rendered documents, biometric templates, consent artefacts. Specify the erasure mechanism for erasable classes (crypto-shredding per subject key, or tombstone) and state what replay returns after an erasure.
3. **Engine purity.** Evaluation is a pure function of **(inputs, rule-set version, evaluation context)**; the evaluation context is enumerated: disbursal date, as-of decision time, jurisdiction set, tax-regime election.
4. **DAG vs fixed point.** The s.2(y) 50% add-back re-bases components that feed its own test, and gross-up is fixed-point ⇒ the calculation graph must permit **bounded fixed-point nodes** (iterate to convergence with a maximum iteration count and a tolerance). Give the add-back as the worked example.
5. **Jurisdiction on the work location** — state, sphere (central/state), and the applicable Code-regime commencement date — not on the employee.
6. **Identity and biometric data.** Aadhaar in a separate, separately-encrypted, separately-access-controlled store referenced by an opaque token (never the number or a hash in business tables); separate keyspace for biometric templates; template entity separate from the attendance event (the record must survive template destruction); **no image column, no image bucket** (enrolment images deleted after template extraction); two-phase device-side erasure with per-device acknowledgement, retry queue **and a documented exception state** (admin attestation of decommission/loss); consent as a versioned first-class entity with whose artefact it is; **two consent regimes run concurrently** across ~May 2027.
7. **AI safety rails.** A mandatory redaction/tokenisation chokepoint on **every** outbound model call (default-deny Aadhaar, PAN, bank account/IFSC, biometric templates), structural in the call graph; LLM prompt/completion logs kept in India (log residency); per-tenant AI kill switch and per-feature opt-out, **default off for RBI/SEBI/IRDAI tenants**; a sub-processor-change gate wired to per-tenant consent; a per-employee AI disclosure record at every call site; human-in-the-loop with a recorded named confirmer for any AI output feeding hiring, appraisal, promotion, PIP or termination.
8. **Incident pipeline** to six hours, with an AI/ML incident class (prompt injection, poisoning, extraction, inference-pipeline access).
9. **PF liability on arrears dates from the disbursal date**, not the wage month — surfaced when the arrears batch is approved.
10. **Per-establishment filing ledger**, unbroken, that refuses silent abandonment (EV-038).
11. **Aadhaar optionality vs filing acceptance.** Aadhaar is optional everywhere, including EPF/ESI flows. Define the behaviour when an employee exercises it and a filing needs seeding: default = **exclude-and-flag with operator and employee notices**, never block payroll; alternatives listed; route final choice to counsel.
12. **Migration consent.** Consent cannot be backfilled. Specify the migration onboarding consent flow: what is captured, in whose name, with which notice text, the non-responder path — separating the SPDI written-consent set (biometrics, financial data) from everything else.
13. **NFRs.** Availability as a **windowed SLO** (proposal: 99.95% from the 25th to the 2nd, 99.5% otherwise) marked [Hypothesis] with rationale from the 20–200 segment; RPO/RTO as provisional assumptions to be replaced by §20 instrumentation.
